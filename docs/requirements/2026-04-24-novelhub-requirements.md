## 1. 文档定位

本文档是一份用于 DDD 实践的纯需求文档，不包含技术设计、数据库设计、消息队列设计、部署方案或代码结构约束。

项目目标是参考起点、番茄等小说连载阅读平台的常见业务形态，抽象出一套适合练习领域分析、领域建模、需求拆分和后续实现的中型项目需求。项目实现规模建议控制在约 30000 行生产代码左右。

## 2. 产品背景

网络小说连载平台连接读者、作者和平台运营方。作者持续创作并发布作品，读者通过分类、榜单、搜索、推荐位等方式发现作品，随后阅读、追更、评论、投票、打赏或订阅。平台负责审核、治理、榜单运营、收益结算和内容分发。

这类业务非常适合用于 DDD 练习，原因包括：

- 作品、章节、书架、订阅、评论、榜单、审核、结算等概念边界清晰。
- 业务状态丰富，例如草稿、待审核、连载中、断更、完结、下架。
- 不同角色的权限差异明显，适合练习用例分析。
- 付费、投票、结算、举报等行为需要严谨的业务规则。
- 多个业务动作会产生后续影响，例如新章节发布后影响书架追更、最近更新、作者数据和读者通知。

## 3. 产品目标

墨卷 NovelHub 的目标不是复刻真实商业平台，而是提供一个完整但可控的小说连载阅读业务样本。

核心目标：

- 读者可以发现、阅读、追更、评论和支持作品。
- 作者可以创建作品、管理章节、发布连载并查看作品表现。
- 平台可以审核内容、处理举报、维护榜单和管理运营规则。
- 系统可以覆盖免费阅读和付费订阅两种商业模式。
- 需求复杂度足够支撑 DDD 的分析、设计和实现练习。

非目标：

- 不接入真实支付渠道。
- 不实现真实推荐算法。
- 不处理真实税务、发票、版权合同和提现。
- 不实现听书、漫画、短剧、AI 写作助手。
- 不实现复杂广告投放系统。
- 不追求高并发商业级性能，只要求业务闭环完整。

## 4. 用户角色

### 4.1 游客

游客是未登录用户。

游客可以：

- 浏览首页推荐内容。
- 查看作品分类和榜单。
- 搜索作品。
- 查看作品详情、目录和免费章节。

游客不可以：

- 加入书架。
- 记录阅读进度。
- 发表评论。
- 投票、打赏或订阅。
- 申请成为作者。

### 4.2 读者

读者是已登录的普通用户。

读者可以：

- 阅读免费章节。
- 订阅付费章节。
- 将作品加入书架。
- 记录阅读进度和书签。
- 接收新章节追更提醒。
- 发表评论、章评和回复。
- 点赞、举报评论。
- 投推荐票、月票。
- 打赏作品。
- 查看自己的订阅记录、消费流水和互动记录。

### 4.3 作者

作者是完成作者资料申请的用户。

作者可以：

- 创建作品。
- 编辑作品资料。
- 创建分卷和章节草稿。
- 保存草稿。
- 立即发布章节。
- 设置定时发布章节。
- 修订已发布章节。
- 将作品标记完结。
- 查看作品数据。
- 查看订阅、打赏和收益统计。
- 管理自己作品下的部分评论，例如置顶或回复。

作者不可以：

- 审核自己的作品。
- 删除平台审计记录。
- 绕过内容审核。
- 修改读者订阅记录。
- 修改平台榜单结果。

### 4.4 运营管理员

运营管理员负责平台治理。

运营管理员可以：

- 审核作品。
- 审核章节。
- 驳回不合规内容。
- 下架作品或章节。
- 解禁作品或章节。
- 处理评论举报。
- 删除违规评论。
- 禁言违规用户。
- 维护分类、标签和推荐位。
- 查看运营数据。

运营管理员的敏感操作必须有原因记录。

### 4.5 系统任务

系统任务代表自动执行的后台行为。

系统任务可以：

- 自动发布到期的定时章节。
- 自动标记长期未更新作品为断更。
- 生成每日榜单。
- 生成作者数据统计。
- 生成月度收益结算。
- 发送站内通知。

## 5. 业务名词

| 名词 | 含义 |
| --- | --- |
| 作品 | 作者创作的一本小说，包含标题、简介、分类、标签、封面和章节目录 |
| 分卷 | 作品目录中的章节分组，例如正文卷、番外卷、作品相关；分卷用于组织目录，不是独立作品 |
| 章节草稿 | 作者未正式发布的章节内容 |
| 已发布章节 | 已对读者开放的章节 |
| 发布序号 | 章节正式发布时由系统分配的作品内唯一递增序号，发布后保持稳定 |
| 目录 | 作品已发布章节按分卷和发布序号组织后的展示列表 |
| 书架 | 读者收藏和追更作品的列表 |
| 阅读进度 | 读者在某作品某章节中的阅读位置 |
| 推荐票 | 读者每日可获得的轻量支持票 |
| 月票 | 与读者消费或活跃资格相关的高价值支持票 |
| 打赏 | 读者向作品表达支持的付费行为 |
| 订阅 | 读者购买某个付费章节阅读权的行为 |
| 追更 | 读者关注连载作品并等待新章节 |
| 审核 | 平台判断作品或章节是否允许公开展示的行为 |
| 下架 | 平台禁止作品或章节继续公开展示的治理行为 |
| 断更 | 连载作品长期未更新后的状态 |
| 完结 | 作者确认作品正文已经结束 |
| 榜单 | 按某种规则生成的作品排行 |
| 结算 | 平台根据订阅、打赏等行为计算作者收益 |

## 6. 需求范围总览

项目建议分为三个阶段交付。

| 阶段 | 目标 | 主要能力 |
| --- | --- | --- |
| P1 内容与阅读闭环 | 让作者能发书，读者能阅读和追更 | 作者入驻、作品管理、章节发布、审核、书架、阅读进度 |
| P2 互动与商业化 | 让读者能互动和付费支持作品 | 评论、章评、推荐票、月票、订阅、打赏、钱包模拟 |
| P3 运营与增长闭环 | 让平台能运营、治理和统计 | 榜单、推荐位、举报处理、通知、作者数据、收益结算 |

## 7. 功能需求

### 7.1 账号与身份

REQ-USER-001：用户可以注册账号并登录平台。

REQ-USER-002：用户注册后默认获得读者身份。

REQ-USER-003：用户可以设置昵称和头像。

REQ-USER-004：用户可以申请成为作者。

REQ-USER-005：作者申请需要填写笔名、作者简介和头像。

REQ-USER-006：作者笔名全站唯一。

REQ-USER-007：用户状态包括正常、禁言、冻结。

REQ-USER-008：被禁言用户可以阅读，但不能评论、回复、投票或举报。

REQ-USER-009：被冻结用户不能登录或执行任何业务操作。

### 7.2 作者入驻

REQ-AUTHOR-001：读者可以提交作者入驻申请。

REQ-AUTHOR-002：作者入驻资料至少包含笔名、头像和简介。

REQ-AUTHOR-003：笔名长度需要在平台允许范围内，并且不能与已有作者重复。

REQ-AUTHOR-004：作者简介不能为空，且不能包含违规内容。

REQ-AUTHOR-005：作者入驻通过后，可以创建作品。

REQ-AUTHOR-006：作者可以修改头像和简介。

REQ-AUTHOR-007：作者修改笔名需要受到频率限制。

### 7.3 作品创建与资料管理

REQ-NOVEL-001：作者可以创建作品。

REQ-NOVEL-002：创建作品时必须填写标题、简介、分类、目标读者和价格模式。

REQ-NOVEL-003：作品可以上传封面。

REQ-NOVEL-004：作品可以设置标签。

REQ-NOVEL-005：同一作者名下不能存在标题完全相同的作品。

REQ-NOVEL-006：作品标题不能为空。

REQ-NOVEL-007：作品简介长度要求为 20 到 500 个字。

REQ-NOVEL-008：作品最多设置 10 个标签。

REQ-NOVEL-009：作品价格模式包括免费和 VIP。

REQ-NOVEL-010：作品目标读者包括男频、女频和通用。

REQ-NOVEL-011：作品创建后初始状态为草稿。

REQ-NOVEL-012：草稿作品仅作者本人和管理员可见。

REQ-NOVEL-013：作者可以修改草稿作品资料。

REQ-NOVEL-014：已发布作品修改标题、简介、封面、分类或标签后，需要重新进入资料审核。

REQ-NOVEL-015：作品资料审核期间，旧资料继续对读者展示。

### 7.4 作品状态

REQ-STATUS-001：作品状态包括草稿、待审核、连载中、断更、完结、下架。

REQ-STATUS-002：草稿作品不能被普通读者阅读。

REQ-STATUS-003：待审核作品不能被普通读者阅读。

REQ-STATUS-004：连载中作品可以发布新章节。

REQ-STATUS-005：作品长时间未更新后，系统可以自动标记为断更。

REQ-STATUS-006：断更作品发布新的正文或番外章节后，状态恢复为连载中。

REQ-STATUS-007：作者可以将连载中或断更作品标记为完结。

REQ-STATUS-008：完结作品不能新增正文章节。

REQ-STATUS-009：完结作品允许修订已发布章节。

REQ-STATUS-010：完结作品允许新增番外章节和作品相关章节，但不因此恢复为连载中。

REQ-STATUS-011：下架作品不在首页、分类、搜索和榜单中展示。

REQ-STATUS-012：下架作品不能被作者继续编辑或发布章节。

REQ-STATUS-013：管理员可以解禁下架作品。

### 7.5 分卷管理

REQ-VOLUME-001：作者可以为作品创建分卷。

REQ-VOLUME-002：分卷拥有标题、类型、简介和展示顺序。

REQ-VOLUME-003：分卷类型包括正文、番外和作品相关。

REQ-VOLUME-004：系统默认提供正文分卷。

REQ-VOLUME-005：默认正文分卷不能被删除。

REQ-VOLUME-006：作者可以创建番外分卷和作品相关分卷。

REQ-VOLUME-007：新书首章必须发布在正文分卷下。

REQ-VOLUME-008：作者可以调整未发布章节所在分卷。

REQ-VOLUME-009：已发布章节调整分卷需要记录操作原因。

REQ-VOLUME-010：已发布章节调整分卷不能改变章节发布序号、订阅权益、章评和阅读进度。

REQ-VOLUME-011：空的自定义分卷可以删除。

REQ-VOLUME-012：存在已发布章节的分卷不能直接删除。

REQ-VOLUME-013：作品相关分卷用于公告、设定、上架感言、请假条等非正文内容。

### 7.6 章节草稿

REQ-DRAFT-001：作者可以创建章节草稿。

REQ-DRAFT-002：草稿可以保存标题、正文、作者的话、章节类型和所在分卷。

REQ-DRAFT-003：草稿允许正文为空。

REQ-DRAFT-004：系统应支持自动保存草稿。

REQ-DRAFT-005：作者可以手动保存草稿。

REQ-DRAFT-006：作者可以删除未发布草稿。

REQ-DRAFT-007：删除草稿后不可被普通恢复。

REQ-DRAFT-008：草稿只能由作品作者本人编辑。

REQ-DRAFT-009：草稿章节类型需要与所在分卷类型匹配。

REQ-DRAFT-010：草稿在发布前可以更换所在分卷。

### 7.7 章节发布

REQ-CHAPTER-001：作者可以将草稿发布为正式章节。

REQ-CHAPTER-002：章节正式发布时，标题不能为空。

REQ-CHAPTER-003：章节正式发布时，正文不能为空。

REQ-CHAPTER-004：单章字数不能超过 20000 字。

REQ-CHAPTER-005：平台建议单章字数为 2000 到 6000 字。

REQ-CHAPTER-006：作品首个正文章节不少于 1000 字，短篇分类不少于 300 字。

REQ-CHAPTER-007：章节发布后获得作品内唯一递增的发布序号。

REQ-CHAPTER-008：发布序号不能重复。

REQ-CHAPTER-009：发布序号不能由作者手动指定。

REQ-CHAPTER-010：发布序号发布后不能因修订、隐藏、撤回或移动分卷而改变。

REQ-CHAPTER-011：正文和番外章节发布成功后，作品总字数、章节数和更新时间同步变化。

REQ-CHAPTER-012：作品相关章节发布成功后，不计入作品总字数和章节数。

REQ-CHAPTER-013：作者的话不计入章节正文字数。

REQ-CHAPTER-014：正文和番外章节发布成功后，加入书架的读者应看到追更提醒。

REQ-CHAPTER-015：正文和番外章节发布成功后，作品出现在最近更新列表。

REQ-CHAPTER-016：作者可以设置章节定时发布。

REQ-CHAPTER-017：定时发布时间到达后，系统自动发布章节。

REQ-CHAPTER-018：定时发布失败时，作者应能看到失败原因。

REQ-CHAPTER-019：完结作品不能发布新的正文章节。

REQ-CHAPTER-020：完结作品可以发布番外章节和作品相关章节。

REQ-CHAPTER-021：下架作品不能发布新章节。

REQ-CHAPTER-022：VIP 作品可以包含免费章节和 VIP 章节。

REQ-CHAPTER-023：作品相关章节默认免费。

REQ-CHAPTER-024：已产生订阅的 VIP 章节调整收费状态需要记录原因。

### 7.8 章节修订与撤回

REQ-REVISION-001：作者可以修订已发布章节。

REQ-REVISION-002：修订章节需要记录修订时间。

REQ-REVISION-003：修订章节需要保留修订前内容快照。

REQ-REVISION-004：修订章节不能改变发布序号。

REQ-REVISION-005：作者可以撤回最新发布的章节。

REQ-REVISION-006：作者不能撤回中间章节。

## 8. 核心业务规则

### 8.1 作品规则

- 作者必须有效，才能创建作品。
- 作品必须有作者。
- 同一作者下作品标题不能重复。
- 作品简介必须为 20 到 500 个字。
- 作品最多设置 10 个标签。
- 作品公开前必须通过审核。
- 草稿和待审核作品不对普通读者展示。
- 下架作品不参与搜索、分类、首页和榜单展示。

### 8.2 章节规则

- 正式章节必须有标题和正文。
- 单章字数不能超过 20000 字。
- 正文首章必须满足最低字数要求。
- 章节发布后必须拥有作品内唯一递增的发布序号。
- 发布序号不能重复，不能由作者手动指定。
- 发布序号发布后不能因修订、隐藏、撤回或移动分卷而改变。
- 分卷用于组织目录，不改变章节所属作品。
- 正文和番外章节计入作品总字数和章节数。
- 作品相关章节不计入作品总字数和章节数。
- 作者的话不计入章节正文字数。
- 作品更新时间等于最新公开正文或番外章节的发布时间或更新时间。
- 完结作品不能新增正文章节。
- 完结作品可以新增番外章节和作品相关章节。
- 下架作品不能新增章节。

### 8.3 阅读权益规则

- 免费章节所有用户可读。
- VIP 章节需要订阅后阅读。
- 作品相关章节默认免费。
- 作者本人可以阅读自己作品的所有章节。
- 管理员可以因审核和治理需要查看章节。
- 普通下架不影响已订阅章节的既有阅读权益。
- 合规强制封禁可以覆盖既有阅读权益。

### 8.4 订阅与钱包规则

- 订阅章节前必须检查余额。
- 余额不足不能订阅。
- 同一读者订阅同一章节只能成功一次。
- 重复订阅不能重复扣款。
- 钱包流水不能被物理删除。
- 金额计算不能使用浮点数。

### 8.5 投票规则

- 推荐票按日发放并按日失效。
- 月票按月统计。
- 月票需要资格。
- 作者不能给自己的作品投票。
- 同一投票行为不能重复计入榜单。

### 8.6 评论治理规则

- 被禁言用户不能评论、回复或举报。
- 评论删除后普通读者不可见。
- 评论删除记录必须保留。
- 举报必须有原因。
- 管理员处理举报必须有处理说明。

### 8.7 结算规则

- 收益按月结算。
- 结算单生成后不可直接修改。
- 结算错误通过冲正修复。
- 作者只能查看自己的结算。
- 管理员可以查看全部结算。

## 9. 典型业务场景

### 9.1 作者发布新书

1. 用户申请成为作者。
2. 作者创建作品并填写资料。
3. 作者创建正文分卷首章。
4. 作者提交作品审核。
5. 管理员审核通过。
6. 作品变为连载中。
7. 读者可以在分类、搜索和首页看到作品。

验收标准：

- 审核通过前，普通读者看不到作品。
- 审核被拒绝时，作者能看到拒绝原因。
- 审核通过后，作品详情页、目录和首章可访问。

### 9.2 作者持续连载

1. 作者创建章节草稿。
2. 作者保存草稿。
3. 作者选择立即发布或定时发布。
4. 章节发布成功。
5. 作品目录追加新章节。
6. 加入书架的读者看到未读提醒。
7. 最近更新列表出现该作品。

验收标准：

- 新章节获得作品内唯一递增的发布序号。
- 作品字数和更新时间正确变化。
- 定时发布重复触发不能产生重复章节。

### 9.3 读者追更作品

1. 读者浏览作品详情。
2. 读者加入书架。
3. 读者阅读当前最新正文或番外章节。
4. 作者发布新的正文或番外章节。
5. 读者书架显示未读章节数。
6. 读者继续阅读后，阅读进度更新。

验收标准：

- 同一作品不能重复加入书架。
- 阅读进度能从上次位置恢复。
- 新章提醒只影响已加入书架的读者。

### 9.4 读者订阅 VIP 章节

1. 读者打开 VIP 章节。
2. 系统提示需要订阅。
3. 读者确认订阅。
4. 系统检查钱包余额。
5. 余额足够时扣款并生成订阅记录。
6. 读者获得章节阅读权。

验收标准：

- 余额不足时订阅失败且不扣款。
- 重复订阅同一章节不会重复扣款。
- 订阅成功后再次打开章节不再提示订阅。

### 9.5 评论举报处理

1. 读者发现违规评论。
2. 读者提交举报并选择原因。
3. 管理员查看举报。
4. 管理员确认举报成立。
5. 管理员删除评论并填写处理说明。
6. 举报人和评论作者收到处理结果。

验收标准：

- 举报必须有原因。
- 删除后的评论普通读者不可见。
- 处理记录可以被管理员追溯。

### 9.6 月度收益结算

1. 月初系统统计上月订阅、打赏和模拟广告收入。
2. 系统为作者生成结算单。
3. 作者查看结算明细。
4. 管理员发现错误时创建冲正记录。

验收标准：

- 同一作者同一月份不能重复生成有效结算单。
- 结算单不能直接修改。
- 冲正记录能清楚说明调整原因。

| 处理举报 | 否 | 否 | 否 | 是 |
| 查看全站运营数据 | 否 | 否 | 否 | 是 |

## 12. 质量需求

虽然本文档不做技术设计，但产品质量上需要满足以下要求：

- 关键业务操作需要有明确成功或失败结果。
- 金额、订阅、投票和结算类操作不能因为重复提交产生重复效果。
- 敏感操作必须可追溯。
- 用户看不到自己无权访问的内容。
- 榜单、作者数据、通知允许延迟，但不能长期不一致。
- 错误提示需要能帮助用户理解失败原因。

## 13. DDD 练习建议

以下内容不是技术设计，只是后续领域分析时可以重点观察的业务边界。

候选业务域：

- 内容创作：作品、分卷、章节、目录、连载状态。
- 阅读追更：书架、阅读进度、书签、未读提醒。
- 商业化：钱包、订阅、打赏、结算。
- 互动社区：评论、章评、回复、点赞、举报入口。
- 发现运营：分类、搜索、榜单、推荐位。
- 审核治理：审核任务、下架、禁言、举报处理。
- 通知：站内信、追更提醒、审核结果通知。

适合练习的问题：

- 作品和章节是否应该是同一个聚合？
- 目录连续性应该由谁保证？
- 订阅扣款和阅读授权如何保持一致？
- 投票是否应该直接修改作品？
- 榜单是核心业务事实还是读模型结果？
- 下架作品如何影响已订阅读者权益？
- 评论删除是物理删除还是状态变化？
- 月度结算为什么不能直接修改？

## 14. 规模边界

建议实现范围控制在约 30000 行生产代码。

建议保留：

- 完整作品和章节生命周期。
- 阅读、书架和追更。
- 免费/VIP 订阅闭环。
- 评论、举报和基础治理。
- 推荐票、月票和榜单。
- 作者数据和月度结算。

建议简化：

- 支付只做模拟钱包。
- 推荐只做榜单和推荐位。
- 搜索只做基础关键词搜索。
- 审核只做人工审核和简单规则。
- 通知只做站内信。
- 结算只做到平台内账单，不做提现。

建议排除：

- 真实支付。
- 真实提现。
- 发票税务。
- AI 写作助手。
- 听书和音频版权。
- 广告投放系统。
- 多租户和多站点。
- 国际化。

## 15. 总体验收标准

项目完成后，应能演示以下闭环：

- 一个普通用户申请成为作者。
- 作者创建作品并提交审核。
- 管理员审核通过作品。
- 作者发布多个章节。
- 读者搜索到作品并加入书架。
- 读者阅读免费章节并记录进度。
- 读者订阅 VIP 章节。
- 读者发表评论、投推荐票或月票、打赏作品。
- 作者查看作品数据和收益。
- 管理员处理一次举报并下架违规内容。
- 系统生成榜单和月度结算。

如果以上闭环都能被清晰演示，并且关键失败场景有对应处理，则认为需求范围完成。
